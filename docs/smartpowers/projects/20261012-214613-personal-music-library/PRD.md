# Product Requirements Document — Rustune

Status: Approved
Approved: 2026-10-12 by user
Last updated: 2026-10-18
Project: 20261012-214613-personal-music-library

## Summary

Rustuneは、iTunes Storeで購入・ダウンロードした楽曲を自分のライブラリへ取り込み、整理・再生する個人用Webアプリ。Spotifyのように楽曲・アルバム・アーティストをたどり、検索やプレイリストから聴ける体験を目指す。

音源はミュージックアプリ（旧iTunes）のメディアフォルダにある、ブラウザで再生可能な購入済み`.m4a`（AAC）ファイルをスキャンしてコピーする。バックエンドはRust、フロントエンドもRustをWASMへコンパイルして構築する。初期版は取り込みから再生までの一連の体験を完成させ、機能を増やしすぎない。

## Problem and outcome

iTunes Storeで買った曲はミュージックアプリでしか快適に聴けず、Apple Musicの曲と混在してしまう。購入済みの曲だけを、自分で管理できる保存先とUIで探して聴けるようにしたい。

購入後にスキャンを実行すると、新しい購入曲がライブラリに追加され、検索・再生できる状態になる。

## Target users

- iTunes Storeで楽曲を購入しており、購入曲を個人ライブラリとして管理したいユーザー。
- 自分でアプリを運用し、音源と管理情報を手元の保存先に保持したいユーザー。
- 初期版は1ユーザー・1サーバー。他人への配信や公開音楽サービスの運営は対象外。

## Scope

### In scope

- 設定した取り込み元フォルダ（既定はミュージックアプリのメディアフォルダ）のスキャンと、購入済み`.m4a`のライブラリへのコピー。
- 未対応形式・破損ファイルの除外。取り込み結果（追加・スキップ・失敗）の表示。
- 重複検出、取り込み元パスと取り込み日時の保持。
- 音源の永続保存、ファイル内メタデータとジャケットの取り込み・編集。
- iTunes Search APIによるメタデータ・ジャケットの補完（ユーザー操作時のみ）。
- 楽曲・アルバム・アーティストの閲覧と検索。
- お気に入り、プレイリスト、再生キュー、ブラウザでの再生。
- デスクトップを主対象とした、日本語のレスポンシブUI。
- 最小限のWeb App Manifestを用意し、Chromeのアドレスバーのインストールアイコンから追加できるUX。OSのメディア操作への対応。
- Macのログイン時のサーバー自動起動。
- Rustによるバックエンドと、Rust/WASMを中心とするフロントエンド。

### Out of scope

- Apple Music等のサブスク曲の取り込み、DRMの解除・回避。
- アプリ内でのiTunes Storeの購入・ダウンロード。購入とダウンロードはミュージックアプリで行う。
- iTunes Search APIの試聴音源の再生・保存。Apple Music API / MusicKitの利用。
- URL指定での音源取得、Webページからの音源抽出、動画サイトからの変換。
- CDからリッピングした曲の取り込み。
- iTunes Store以外のストア（mora、Bandcamp等）の購入曲への専用対応。初期版では後述の形式要件を満たすファイル以外は扱わない。
- ミュージックアプリと別のマシン（NAS、VPS等）でのサーバー運用。
- ブラウザからのファイルアップロード、サーバーから端末へのファイル書き出し、アプリ内オフライン再生。
- ミュージックアプリへの書き戻し、ミュージックアプリのプレイリストや再生回数の同期。
- 複数ユーザー、他人への公開・配信、共有プレイリスト、SNS、課金、楽曲推薦。
- ネイティブアプリ、Electron・Tauri等によるデスクトップアプリ化。
- Service Worker、オフライン動作、音源キャッシュ。インストール用Web App Manifestは対象に含む。Safariの「Dockに追加」での動作保証。
- 複数端末の再生同期、歌詞、音声解析、ギャップレス再生、形式変換。

## Functional requirements

Mustは初期版の成立に必要な機能、Shouldは初期版で優先するが削減可能な機能。

| ID | Priority | Requirement | Acceptance criteria |
| --- | --- | --- | --- |
| REQ-001 | Must | 取り込み元フォルダをスキャンし、購入済み楽曲をライブラリへコピーする | UIからスキャンを開始するとジョブIDが返り、画面を閉じても処理が続く。取り込み元配下の対象ファイルがライブラリの保存先へコピーされ、1ファイルにつき1曲追加される。取り込み元のファイルは変更・削除されない |
| REQ-002 | Must | 取り込み状況と結果を確認できる | 待機中・実行中・完了・失敗を区別できる。実行中は処理済み件数と総数を表示する。完了時に追加・スキップ（理由別）・失敗の件数と対象ファイルを確認できる |
| REQ-003 | Must | 中断・再起動後も取り込み状態が整合する | サーバー再起動後に未完了ジョブが実行中のまま放置されず、再実行できる。再実行時は取り込み済みの曲を再コピーしない。コピー途中のファイルは再生可能な楽曲として表示されない |
| REQ-004 | Must | 重複を作らず、取り込み元を保持する | 同じフォルダを再スキャンしても曲が増えない。同じ音源ファイルを別パスにコピーしても重複作成しない。取り込み元のパスと取り込み日時を確認できる |
| REQ-005 | Must | メタデータを取り込み、修正できる | ファイルからタイトル・アーティスト・アルバム・アルバムアーティスト・ディスク/曲順・再生時間・ジャケットを表示する。欠落時にも仮タイトルと既定画像で閲覧できる。タイトル・アーティスト・アルバム・曲順を編集し、再起動後も保持する。編集は再スキャンで上書きされない |
| REQ-006 | Must | ライブラリを閲覧・検索できる | 楽曲一覧、アルバム別、アーティスト別の表示があり、タイトル・アーティスト・アルバムの部分一致で検索できる。空状態と検索結果なしを区別して案内する |
| REQ-007 | Must | ブラウザで音楽を再生できる | 初期対応形式は`.m4a`（AAC）。選んだ曲の再生・一時停止・シーク・音量調整ができ、再生時間を表示する。画面内のページ移動で再生が途切れず、再生失敗時に理由を表示する |
| REQ-008 | Must | 再生キューを操作できる | アルバムまたはプレイリストを順番に再生し、前後の曲へ移動できる。曲の終了で次曲へ進み、任意の曲をキュー末尾に追加できる |
| REQ-009 | Must | プレイリストを作成・編集できる | 名前を付けたリストを作成し、曲の追加・除去・並べ替え・リスト削除ができる。変更は再起動後も保持し、リスト削除で元の音源は消えない |
| REQ-010 | Should | お気に入りを管理できる | 曲のお気に入りを切り替え、一覧から再生できる。状態は再起動後も保持する |
| REQ-011 | Must | 不要な楽曲を削除できる | 確認後、ライブラリの楽曲と保存音源を削除し、プレイリストと再生キューの参照も整理する。取り込み元のファイルは削除しない。削除した曲は再スキャンで再取り込みされない（取り込み対象に戻す操作を提供する）。部分失敗時には成功と表示せず、再操作できる |
| REQ-012 | Must | 取り込めないファイルを識別して除外する | 音声でないファイル、未対応形式、破損ファイル、サイズ超過、容量不足を識別し、スキップまたは失敗として理由を示す。除外したファイルから再生可能な楽曲を作成しない。ブラウザで再生できない音源は再生時にエラーを表示する |
| REQ-013 | Should | iTunes Search APIでメタデータとジャケットを補完できる | アルバムまたは曲を選んで補完を実行すると候補を表示し、ユーザーが選んだ場合のみ反映する。ジャケットはAPIが返す解像度（60×60・100×100等）でよく、高解像度を必須としない。API不通・該当なし・画像なしの場合も既存情報は変わらず、理由を表示する。試聴音源は取得・再生しない |
| REQ-014 | Must | 新しい購入曲を自動で取り込める | 取り込み元に追加された対象ファイルが、手動操作なしで一定時間内（既定値は設計時に定める）にライブラリへ追加される。サーバー停止中に追加されたファイルは起動後に取り込まれる。ダウンロード途中のファイルは完了後に取り込む。自動取り込みの結果もREQ-002と同様に確認できる。設定で無効化でき、既定は有効 |
| REQ-015 | Must | Chromeのアプリとしてインストールして違和感なく使える | インストール用Manifestを提供し、未インストールのChromeでアドレスバーのインストールアイコンから追加できる。表示条件はChromeに従い、メニューからの導線も案内する。Rustuneの名前とアイコンでDock・アプリケーションフォルダに入り、アドレスバーのない独立ウィンドウで開く。アプリ内操作ですべての画面を行き来できる。タイトルが現在の画面または再生中の曲を示す。小さいウィンドウでも主要操作が隠れない。外部リンクは通常のブラウザで開く |
| REQ-016 | Must | OSのメディア操作で再生を制御できる | 再生中は、Macのコントロールセンター（「再生中」）に曲名・アーティスト・アルバム・ジャケットが表示される。キーボードのメディアキーとコントロールセンターから、Rustuneのウィンドウが前面になくても再生・一時停止・前後の曲への移動ができる |
| REQ-017 | Must | Macのログイン時にサーバーを自動起動できる | 運用手順に沿って設定すると、Macへのログイン後に手動操作なしでサーバーが起動し、アプリから利用できる。異常終了時は自動で再起動する。設定と解除の手順を運用手順に明記する |

## Non-functional requirements

| ID | Area | Requirement | Measure |
| --- | --- | --- | --- |
| NFR-001 | 技術制約 | サーバーのアプリケーションロジックをRustで実装する | 設計と実装レビューで、取り込み処理・ライブラリ管理・配信を担うRustコードを確認できる |
| NFR-002 | 技術制約 | フロントエンドの画面・状態管理・操作ロジックをRust/WASMで構築する | 主要画面と操作がRustソースから構築される。HTML/CSS、生成バインディング、ブラウザAPI連携用の最小限のJavaScriptは許容する。音声デコード自体をWASM化することは必須にしない |
| NFR-003 | 性能 | 個人ライブラリで検索・閲覧を待たせない | 仮の評価条件は4 CPU・8 GBメモリ・SSD、1万曲、同時利用1人、LAN。初回ロード後の一覧・検索結果表示は操作からp95で1秒以内。取り込み実行中も閲覧・再生を継続できる。測定手順と固定環境は設計時に定める |
| NFR-004 | 再生 | 保存済み音源を速やかに再生する | 同評価環境でAACの再生開始が操作からp95で2秒以内。曲全体のダウンロード完了を待たずに再生できる |
| NFR-005 | 永続性 | 音源と管理情報を再起動後も利用できる | 取り込み済みの音源・編集内容・プレイリストが再起動後も使える。取り込み元のファイルを削除・移動しても再生できる。バックアップ手順に沿った復元でこれらを再現できる |
| NFR-006 | 取り込み元の安全性 | 取り込み元を読み取り専用として扱い、設定外の場所を読まない | 取り込み元のファイルを書き換え・移動・削除しないことをテストで確認する。設定したフォルダ外を指すシンボリックリンク等をたどらない |
| NFR-007 | 資源制限 | 取り込みで保存領域や処理を占有し続けない | 暫定既定値は1ファイル200 MiB・保存先の空き容量下限1 GiB。上限・下限に達したファイルはスキップまたは失敗として表示する。値は設定可能にする。iTunes Search APIはAppleの目安（約20回/分）を超えて呼び出さない |
| NFR-008 | アクセス範囲 | 個人用としてアクセス範囲を限定できる | 初期版はlocalhostまたは運用者がアクセス制御する私設ネットワークで利用する。認証なしのインターネット公開を前提にしない。設定・運用手順に公開範囲と、購入音源を他人に配信しない旨を明示する |
| NFR-009 | UI・互換性 | 日常操作を日本語UIとキーボードで行える | 幅1280pxと390pxで主要操作が可能。ボタンにラベルとフォーカス表示があり、取り込み・検索・再生・プレイリスト編集をキーボードで行える。受け入れ時点の安定版Chrome・Firefox・Safariで確認し、バージョンを記録する |
| NFR-010 | 運用・プライバシー | 取り込み失敗を調査でき、購入者情報を露出しない | ジョブIDとファイルパスで状態と失敗理由をログで追跡できる。購入ファイルに埋め込まれたApple IDの氏名・メールアドレス等をUI・API応答・通常ログに出さない |

## User journeys

1. 購入曲を追加する：iTunes Storeで購入し、ミュージックアプリでダウンロードする → Rustuneでスキャンを実行する → 結果（追加・スキップ）を確認する → 追加された曲を再生する。
2. 音楽を整理する：取り込んだ曲の情報を修正する、または補完する → アルバムやアーティストで探す → プレイリストに追加し、順序を変更する。
3. 続けて聴く：DockからRustuneを起動する → 検索結果から再生する → 別画面で曲を探す → キューに追加する → 別のアプリで作業しながら、メディアキーで次の曲へ進む。
4. 取り込めなかった曲を確認する：スキップ理由（未対応形式、破損等）を読む → 対応するAACファイルがローカルに保存されているか確認する → 再スキャンする。

## Assumptions and constraints

- 承認済み変更（2026-10-18 by user）：Chromeのインストールアイコンから追加するため、最小Web App Manifestを導入する。Service Worker・オフライン再生は対象外のまま。

- 承認済み変更：ジャケット補完は低解像度を許容し、高解像度の取得要件を外す（ユーザーの「そこは妥協していいよ」に基づく）。補完機能の優先度はShouldのまま。
- ユーザーが明示した方針：音源はiTunes Storeで購入・ダウンロードした、ブラウザで再生可能な`.m4a`（AAC）ファイルを使う。Rustバックエンド、WASMを重視したフロントエンド。個人利用のみ。
- 承認済み変更（2026-10-17 by user）：DRMの専用検査・判定を要件から外す。同じ曲を実際に取得し直す比較と、その場合の同一性保証も外す。再スキャンと同じ音源ファイルの別パスコピーに対する重複防止は維持する。
- 前提：購入とダウンロードはユーザーがミュージックアプリで行う。iTunes Storeには購入・フル尺ダウンロードの公開APIはない。
- 決定事項：サーバーはミュージックアプリと同じMacで動かす。既定の取り込み元は`~/Music/Music/Media.localized/Music/`とし、設定で変更できる。
- 暫定前提：取り込み元とライブラリは独立する。取り込み後にミュージックアプリ側で編集・削除しても、ライブラリには反映しない。
- 決定事項：対象はiTunes Storeの購入曲のみで、初期対応形式はAAC（`.m4a`）。CDリッピング曲は考慮しない。
- iTunes Search APIは認証不要の公開APIで、利用規約上、試聴音源はストアの販売促進目的に限られる。本アプリではメタデータとジャケットの補完にのみ使う。
- Rust/WASMを積極的に利用するが、表示・音声出力・ユーザー操作にはブラウザAPIとの連携を許容する。
- 2026-10-12の調査時点でリポジトリにコードはなく、このPRDとPROJECT.mdのみ存在する。
- 要件フェーズではフレームワークや保存方式を決定しない。PRD承認後に、Rust/WASM UI、Rustサーバー、管理データ保存、音源保存、取り込みジョブ、音声配信の選択肢と境界を比較し、DESIGN_DOC.mdに記載する。

## Success measures

- iTunes Storeで購入した10曲以上を取り込み、再起動後も検索・再生できる。
- 未対応形式・破損ファイルは理由付きで除外される。ブラウザでの再生失敗は画面で確認できる。
- 同じフォルダの再スキャンと同じ音源ファイルの別パスコピーで、重複曲を作らない。
- 取り込みからメタデータ編集、プレイリスト作成、連続再生までをUIだけで完了できる。
- Macの再起動後、Dockから起動したRustuneで手動操作なしに再生でき、メディアキーで操作できる。
- 取り込み途中の再起動、破損ファイル、容量不足、サイズ超過の検証で状態が破綻せず、取り込み元のファイルが変化しない。
- 上記Must要件と非機能要件を満たす。Should要件の延期は明記する。

## Risks

- ミュージックアプリのフォルダ構成や設定（メディアフォルダの場所、「ライブラリに追加時にファイルをコピー」の有無）によって、購入曲が既定の場所にないことがある。取り込み元を設定可能にし、初回に対象件数を確認できるようにする。
- 購入曲がクラウド上にあるだけでダウンロードされていない場合、取り込めない。ジャーニー4と運用手順で、ダウンロードが必要なことを案内する。
- 購入ファイルには購入者のApple ID情報が埋め込まれている。外部に出さないことをNFR-010で担保し、ファイル書き出しは対象外とする。
- 欲しい曲がiTunes Storeで販売されていない場合がある。他ストアからの取り込みは後続で検討する。
- iTunes Search APIは仕様変更・提供終了・レート制限があり得る。補完機能はShouldとし、なくても基本機能が成立するようにする。
- Firefoxの一部環境ではAACの再生がOSのデコーダに依存する。受け入れ時に各ブラウザで実機確認する。
- WASM主体のUIでの初回ロード量とブラウザAPI連携が技術選択を左右する。設計フェーズで小さな検証の必要性を判断する。

## Open questions

以下は回答がなければ記載した暫定前提で進められる。変更時は影響する要件を更新する。

- スマートフォンのバックグラウンド再生やアプリ内オフライン再生は、後続の機能追加でよいか。初期案では対象外。
